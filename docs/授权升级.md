# 授权升级说明

本页适用于升级到 v2.0.3.5 的已有安装，以及需要使用 Pro 的 Linux Docker 部署。

**长期授权权益不变，不改成按天订阅。** 系统仍需定期联网验证授权；短期断网不等于授权被取消。请保持服务器时间正确、授权服务可访问，不要靠删除授权数据或重装处理验证失败。

## 先做这三件事

1. **先确认授权服务已完成对应升级，再更新平台。** 授权服务由管理员维护，普通用户不需要自行部署；使用自建授权服务时，请先向维护者确认。
2. **备份原来的完整数据和部署配置。** 包括 `data`、`sessions`、`plugins`、Compose 文件，以及实际使用的 `.env`、覆盖文件和额外挂载目录。重要更新前短暂停止系统再备份，备份使用新文件名，不覆盖上次备份。
3. **保留同一套安装。** 在原部署目录更新，保留原数据挂载、Compose 服务名（如 `awbotnest`）、`container_name`、网络和端口。不要另建空数据目录，也不要让两套实例同时使用同一授权或 Telegram 会话。

## 一键安装用户

重新执行原来的一键命令，选择**原来的安装目录、网络模式和端口**：

```bash
curl -fsSL https://raw.githubusercontent.com/AWdress/AWBotHub/main/install.sh | sudo bash
```

请在**运行本机 Linux Docker 服务的主机**执行，不要在容器终端内执行。安装器会先核对 Docker 实际连接位置，仅接受本机标准套接字，再检测这台主机上可用的稳定标识并以只读方式挂载。远程 Docker context、`DOCKER_HOST`、Docker Desktop 或特殊套接字不会继续安装；请先 SSH 到 Docker 所在 Linux 主机，或使用手动 Compose，不要在另一台电脑上代为读取主机标识。若使用自定义 Compose，请先备份；脚本生成的运行覆盖文件也要保留，后续命令使用相同的配置文件组合。

没有检测到可用标识时，平台仍可启动，网页管理和免费内置插件仍可用，但 Pro 验证不能完成。请让服务器管理员检查，不要随意生成标识、复制别台机器的标识，或使用容器编号代替。

## Linux 手动 Compose 用户

以下步骤在**运行 Docker 服务的 Linux 主机**执行，而不是在容器内执行。远程 Docker、NAS 或虚拟机部署，请先确认自己操作的是正确的主机。Windows、macOS 的 Docker Desktop 不要直接照抄 Linux 主机路径；需要 Pro 时，先确认可用的部署方式。

### 1. 检查主机标识，不显示标识内容

先检查常见位置 `/etc/machine-id`。下面只输出“通过”或“不可用”，不会打印实际标识：

```bash
if [ -f /etc/machine-id ] && [ ! -L /etc/machine-id ] &&
   [ -r /etc/machine-id ] &&
   awk 'NR == 1 && /^[0-9A-Fa-f]+$/ && length($0) == 32 && $0 !~ /^0+$/ {ok=1; next} {ok=0} END {exit !ok}' /etc/machine-id; then
  printf '%s\n' '主机标识检查通过'
else
  printf '%s\n' '主机标识不可用，请先联系服务器管理员检查'
fi
```

显示“不可用”时先停止后续 Pro 更新操作。部分发行版使用 `/var/lib/dbus/machine-id`，由管理员确认该文件是本机的有效普通文件后，可用同样的方法检查，并将下面挂载的 `source` 改为这个实际路径。不要将标识文件复制进 `data`，也不要用随机值、容器 hostname 或 MAC 地址替代。

### 2. 在原服务中补充只读挂载

打开原来的 `docker-compose.yml`，在**原系统服务的 `volumes` 列表下新增一项**。保留已有插件、会话和数据挂载；不要用这段片段替换整个文件：

```yaml
services:
  awbotnest:
    # 保留原来的 image、container_name、environment、ports 等配置。
    volumes:
      - ./plugins:/app/plugins
      - ./sessions:/app/sessions
      - ./data:/app/data
      - type: bind
        source: /etc/machine-id
        target: /run/awbothub/host-machine-id
        read_only: true
        bind:
          create_host_path: false
```

示例中的 `awbotnest` 是 Compose 服务名，不是容器名；实际服务名不同时，保留自己的服务名，并相应替换后续命令。原数据位于其他绝对路径或使用命名卷时，也必须保留原挂载，不要改成示例的相对路径。

`create_host_path: false` 用来避免路径写错时自动新建目录。若 Compose 不支持该配置，先升级 Compose，不要删掉检查继续启动。`source` 必须是上一步确认过的宿主机文件，`read_only: true` 不要去掉。

### 3. 校验配置，拉取镜像并重建原服务

进入**原来的部署目录**。镜像使用 `awdress/awbothub:latest`；需要固定版本时选择已发布的正式标签。

```bash
cd /opt/AWBotNest &&
docker compose config -q &&
docker compose pull awbotnest &&
docker compose up -d awbotnest
```

目录和服务名按原部署替换。上一步失败时，后面的更新命令不会继续执行；先处理错误，不要删除数据或另建实例。这里重建的是原服务，已有持久化数据会继续使用，不需要执行删除卷命令。

如果原部署使用 `docker-compose.awbotnest-runtime.yml`，上面三条命令都要带上同样的文件列表，例如：

```bash
docker compose -f docker-compose.yml -f docker-compose.awbotnest-runtime.yml config -q &&
docker compose -f docker-compose.yml -f docker-compose.awbotnest-runtime.yml pull awbotnest &&
docker compose -f docker-compose.yml -f docker-compose.awbotnest-runtime.yml up -d awbotnest
```

其他自定义覆盖文件同理，使用原来完整的 `-f` 列表，不要遗漏。

### 4. 核对挂载和授权

按原容器名检查只读挂载，示例使用 `AWBotHub`：

```bash
docker inspect AWBotHub --format '{{range .Mounts}}{{if eq .Destination "/run/awbothub/host-machine-id"}}{{.Type}} {{.Source}} {{.Destination}} RW={{.RW}}{{println}}{{end}}{{end}}'
```

应看到已确认的宿主机路径、目标路径和 `RW=false`，不会显示标识内容。没有输出，或显示 `RW=true` 时，先检查配置文件组合与挂载，再重新创建原服务。

然后打开网页，进入“系统设置 → 账号与凭据 → 系统授权”，检查状态。保留原数据且仍在同一主机的安装，会使用原安装信息向授权服务重新验证；若提示需要重新授权，按页面提示填写自己的有效激活码。随后检查已有插件的启用状态和日志。

## 没有恢复 Pro 时怎么查

- **未挂载或标识不可用：** 按上面步骤检查 Docker 主机、文件和实际容器挂载。平台不会悄悄退回使用容器编号，网页管理和免费内置插件不受此限制。
- **时间或网络异常：** 校准服务器时间，检查系统能否访问授权服务，再重试。不要回拨时间或反复删除安装信息。
- **提示绑定其他系统：** 核对是否误用了空数据目录或换了服务器。换机前先停旧实例，并联系授权管理员按流程解绑；复制数据不等于取得另一份授权。
- **已授权但插件同步失败：** 另查 GitHub 网络、限流和插件日志；下载失败不需要更换激活码。

请勿公开实际主机标识、激活码、授权凭证、配置包或完整数据目录。向维护者反馈时只提供脱敏提示、系统版本和部署方式。

## 关于回退

完成新版联网授权验证后，授权状态和服务协议已更新，**不能只改镜像标签退回旧客户端，也不能直接退回旧授权服务**。需要回退时，先停止相关实例，联系维护者制定平台、授权服务和相应一致备份的整体恢复方案；不要通过清空授权数据尝试降级。
